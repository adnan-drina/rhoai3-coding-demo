# OCP machine management

Thin skill: repo decisions and pitfalls here, product behavior in the linked
OpenShift Container Platform 4.22 sections. Detailed record:
`gitops/stages/020-gpu-infrastructure-private-ai/020-gpu-machinesets/README.md`.

## When to use

- A change touches `020-gpu-machinesets/*.yaml`, the `020-gpu-machinesets`
  Application, or `stages/020-gpu-infrastructure-private-ai/generate-gpu-machineset.sh`.
- GPU workers must be added, parked at zero, resumed, or moved to another zone.
- A GPU Machine stays `Provisioning` or fails with a capacity or policy error.

## Repo decisions

| Decision | Where in Git | Official section |
|---|---|---|
| GPU pools are Machine API MachineSets generated by copying the active CPU worker pool of the same zone (AMI, subnet, security groups, IAM profile, user data) and changing name, labels, instance type and disk | `020-gpu-machinesets/machineset-rtxpro6000.yaml`, `020-gpu-machinesets/machineset-gpu.yaml`, `stages/020-gpu-infrastructure-private-ai/generate-gpu-machineset.sh` | [Managing compute machines with the Machine API][machine-api] |
| Default pool RTX PRO 6000 `g7e.2xlarge`, one MachineSet per `us-east-2` zone; optional L40S `g6e.2xlarge` pool in the source zone | `020-gpu-machinesets/` | [Managing compute machines with the Machine API][machine-api] |
| Node labels `cluster-api/accelerator` (`nvidia-rtxpro6000`, `nvidia-gpu`) and `node-role.kubernetes.io/gpu`, taint `nvidia-gpu-only:NoSchedule` on the machine template | `020-gpu-machinesets/` | [Modifying a compute machine set][modify] |
| 200 GB encrypted `gp3` root volume (a 100 GB worker hit kubelet DiskPressure on a ~36 GB model image) | `generate-gpu-machineset.sh` | [Modifying a compute machine set][modify] |
| Replicas are 0 in Git; scripts own the live count; Argo CD ignores `/spec/replicas` with `RespectIgnoreDifferences` | `gitops/applications/020-gpu-machinesets.yaml`, `scripts/platform/resume-gpu-demo.sh`, `scripts/platform/gpu-capacity-probe.sh` | [Manually scaling a compute machine set][scale] |
| No `ClusterAutoscaler`, `MachineAutoscaler` or `MachineHealthCheck`; the accelerator label serves Kueue flavors and scripts only | (none declared) | [Applying autoscaling to an OpenShift Container Platform cluster][autoscale], [Deploying machine health checks][mhc] |
| MachineSets carry `argocd.argoproj.io/sync-options: Prune=false,Delete=false`; removing a pool is a manual step | `020-gpu-machinesets/` | [Deleting a machine][delete] |
| CPU worker and control-plane pools are provisioner-owned; the stages never scale them; `require-node-sizing.sh` fails a deploy on control-plane or CPU workers under 16 vCPU / 60 GiB | `scripts/platform/require-node-sizing.sh` | [Overview of machine management][overview] |

Paths are relative to `gitops/stages/020-gpu-infrastructure-private-ai/` unless they start with `gitops/`, `stages/` or `scripts/`.

## Procedure

1. Regenerate pools from the live CPU pool, review, then write:
   `stages/020-gpu-infrastructure-private-ai/generate-gpu-machineset.sh --source <cpu-machineset>`
   (prints), then the same with `--write` (writes both pool files and the
   replica exceptions in the Application manifest). Never hand-edit provider
   specs: `deploy.sh` refuses a MachineSet whose provider spec drifted from
   its source pool beyond type and disk.
2. Deploy and validate: `./stages/020-gpu-infrastructure-private-ai/deploy.sh`,
   then `./stages/020-gpu-infrastructure-private-ai/validate.sh` (reviewed
   instance types, ready replicas, one GPU per Ready node, taint present; node
   checks fail by design while pools are at zero).
3. Scale only through the scripts, after the OpenShift safety guard in `AGENTS.md`:

   ```bash
   scripts/platform/resume-gpu-demo.sh status
   scripts/platform/resume-gpu-demo.sh resume        # GPU_POOL=l40s for the L40S pool
   scripts/platform/resume-gpu-demo.sh down
   scripts/platform/gpu-capacity-probe.sh             # one zone at a time, back to 0
   oc get machinesets,machines -n openshift-machine-api -L cluster-api/accelerator
   ```

## Pitfalls

- A Machine API MachineSet launches in exactly one subnet and zone; AWS
  `InsufficientInstanceCapacity` makes the Machine retry the same zone
  forever. Scale another zone's MachineSet and park the stuck one at zero
  (`docs/TROUBLESHOOTING.md#gpu-machine-stays-provisioning-or-fails-capacity-or-spot-policy`).
- MachineSet template changes (disk, labels, taint) apply only to new
  Machines; recreate GPU machines after a template change
  (`docs/TROUBLESHOOTING.md#model-image-pull-stalls-on-a-gpu-node`).
- `RespectIgnoreDifferences` protects only existing MachineSets: a new
  MachineSet is created with the Git value, so Git must stay at `replicas: 0`.
- Spot MachineSets are denied by the AWS organization's service control
  policy; nothing in the cluster can lift it.
- Infrastructure name, AMI, zones and tags are cluster-specific; a new
  cluster needs regenerated files.
- Missing GPU nodes: `docs/TROUBLESHOOTING.md#gpu-nodes-do-not-appear`,
  `docs/TROUBLESHOOTING.md#demo-was-restarted-with-zero-gpu-nodes`.
