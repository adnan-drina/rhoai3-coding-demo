# MTA Custom Rule Exercise

## Purpose

Turn a reviewed modernization standard into a small custom MTA rule draft, then evaluate the rule before it influences analysis results.

This exercise is documentation-only. Do not add generated rules to a production ruleset until the standards source, expected matches, validation output, and human approval are recorded.

## Standards Source

Use an approved corporate standards document when one is available. If no approved source has been selected for the demo, use the following demo placeholder only to practice the workflow:

```text
Demo standard excerpt, not real corporate policy:
Applications must not depend on Maven system-scoped JARs from a repository-local lib directory. Internal libraries must be published to an approved artifact repository and referenced by normal Maven coordinates so dependency provenance, SBOM generation, and vulnerability analysis can operate consistently.
```

Before live use, replace the placeholder with an approved source and cite the exact passage used.

## Candidate Demo Rule

For the placeholder standard, the candidate rule intent is:

```text
Detect Maven dependencies that use system scope with a systemPath under a repository-local lib directory.
```

Expected match:

```xml
<dependency>
  <groupId>com.example.internal</groupId>
  <artifactId>audit-logging-library</artifactId>
  <version>1.0.0</version>
  <scope>system</scope>
  <systemPath>${project.basedir}/lib/audit-logging-library-1.0.0.jar</systemPath>
</dependency>
```

Known non-match:

```xml
<dependency>
  <groupId>com.example.internal</groupId>
  <artifactId>audit-logging-library</artifactId>
  <version>2.0.0</version>
</dependency>
```

## Agent Instruction

```text
Use only the cited standards passage and the provided expected match/non-match examples. Propose the smallest MTA custom rule that detects Maven system-scoped dependencies pointing to repository-local lib JARs. Explain ruleID, labels, category, effort, condition, message, false positives, false negatives, and validation approach before producing YAML. Do not apply or commit the rule until a human approves it.
```

## Scribe MCP Instruction

```text
Use Scribe only after the rule intent packet is complete. Generate the smallest useful Konveyor rule, validate it with Scribe, and report expected matches, known non-matches, false-positive risk, category, effort, labels, and review evidence. Do not commit the rule until a human approves it.
```

## Review Gate

The generated rule draft must pass these checks:

- cites the approved standards source;
- has unique rule ID and clear labels;
- uses the correct MTA category and effort;
- contains a specific message that tells a developer what to do;
- matches the expected-bad example;
- does not match the expected-good example;
- records false positives and false negatives;
- passes Scribe validation if Scribe is used;
- passes MTA validation or an MTA analysis run before promotion;
- is reviewed by a human before entering a shared ruleset.

## Promotion Decision

Use one of these outcomes:

- `accept for demo`: rule is safe enough for the controlled exercise;
- `edit`: rule intent is valid but YAML or metadata must change;
- `reject`: rule is unsupported or too broad;
- `defer`: standards source, examples, or validation are insufficient.
