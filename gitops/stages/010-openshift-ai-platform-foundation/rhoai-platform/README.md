# OpenShift AI platform configuration (`010-rhoai-platform`)

This Application owns the shared OpenShift AI singletons: the DSCInitialization `default-dsci`, the
DataScienceCluster `default-dsc`, the `Auth` resource and the dashboard configuration `odh-dashboard-config`. In Stage
010 it turns on the Dashboard, Workbenches and the native observability stack. It also sets up the group-based access.
Later stages turn on their own components on the same DSC and dashboard configuration through a delegation model,
described under [How](#how).

| | |
|---|---|
| Argo CD Application | `010-rhoai-platform` ([manifest](../../../applications/010-rhoai-platform.yaml)) |
| Deployed by | [`stages/010-openshift-ai-platform-foundation/deploy.sh`](../../../../stages/010-openshift-ai-platform-foundation/deploy.sh) (deploy-order 2) |
| Validated by | [`validate.sh`](../../../../stages/010-openshift-ai-platform-foundation/validate.sh) (DSCI, DSC and Auth Ready; monitoring fields; `observabilityDashboard`; foundation component ownership; dashboard route); [`validate-foundation-services.sh`](../../../../stages/010-openshift-ai-platform-foundation/validate-foundation-services.sh) (metrics query and one synthetic trace round trip) |
| Sync | Automated, prune and self-heal; `CreateNamespace`, `SkipDryRunOnMissingResource`, `RespectIgnoreDifferences`; Server-Side Diff via annotation; `ignoreDifferences` on the DSC and the OdhDashboardConfig |
| Depends on | `010-rhoai-operator` (CRDs and controller); `010-observability-operators` (COO, OpenTelemetry and Tempo CRDs for `spec.monitoring`) |
| Used by | All later stages: 020 (Kueue), 030 (KServe, model registry, catalogs), 040 (AI Gateway/MaaS, OGX, Gen AI Studio), 050 (TrustyAI, MLflow, AI pipelines, evaluation), 060 (MCP lifecycle, AgentOps); `010-access` (Auth groups) |

## Why

The RHOAI operator configures the platform through a DSCInitialization (platform-wide settings such as the
applications namespace, monitoring and the trusted CA bundle) and a DataScienceCluster (one `managementState` per
component) [1]. The DataScienceCluster, DSCInitialization and `Auth` are cluster singletons. OpenShift AI 3.5 sets
dashboard access groups in the `Auth` resource (`spec.adminGroups`, `spec.allowedGroups`), and the dashboard
`groupsConfig` field is read-only [2]. Dashboard features are switched with `spec.dashboardConfig` in
`odh-dashboard-config` [2]. The native observability stack is enabled in `DSCInitialization.spec.monitoring` [3].

These singletons change together and have one owner, so they form one Application. The operator lifecycle sits in
`010-rhoai-operator`, and project-level access sits in `010-access`.

## What

| Kind | Name | Namespace | Wave | Purpose |
|---|---|---|---|---|
| Namespace | `redhat-ods-monitoring` | (cluster) | 1 | Monitoring namespace, created before the DSCI with `openshift.io/cluster-monitoring: "true"`. The operator also labels it `opendatahub.io/generated-namespace` |
| DSCInitialization | `default-dsci` | (cluster) | 2 | Applications namespace `redhat-ods-applications`; monitoring `Managed` in `redhat-ods-monitoring`; trusted CA bundle `Managed` |
| DataScienceCluster | `default-dsc` | (cluster) | 3 | `dashboard` and `workbenches` Managed; every other component `Removed` in Git (see delegation) |
| Auth | `auth` | (cluster) | 4 | `adminGroups: [rhods-admins]`, `allowedGroups: [rhods-admins, rhoai-developers]` |
| OdhDashboardConfig | `odh-dashboard-config` | `redhat-ods-applications` | 4 | Foundation dashboard flags (see How) |
| Config (`imageregistry.operator.openshift.io`) | `cluster` | (cluster) | 0 | Partial manifest: `spec.defaultRoute: true` only, `Prune=false,Delete=false`; exposes the internal registry route that Stage 050 OCI export uses |

The kustomization adds `SkipDryRunOnMissingResource=true` to every object. There are no hooks.

Not in Git (generated by the RHOAI operator from these CRs): the `redhat-ods-applications` and `rhods-notebooks`
namespaces, the per-component CRs (`*.components.platform.opendatahub.io`), the `Monitoring` service
`default-monitoring`, the `MonitoringStack`, `ThanosQuerier`, `TempoMonolithic` `data-science-tempomonolithic`,
`OpenTelemetryCollector` `data-science-collector` and the `PersesDatasource` objects in `redhat-ods-monitoring`. The
operator also creates the `rhods-admins` Group from the `Auth` CR. Its membership is set by `setup-access.sh`, not Git.

## How

**DSCInitialization.**
`default-dsci` exists in Git because the operator's automatic creation is disabled (`DISABLE_DSC_CONFIG=true` in
[`010-rhoai-operator`](../rhoai-operator/README.md)). The monitoring block follows the documented example field by
field [3]:

| Field | Value | Documented meaning [3] |
|---|---|---|
| `monitoring.managementState` | `Managed` | Enables and manages the observability stack |
| `monitoring.namespace` | `redhat-ods-monitoring` | Namespace for the monitoring components (documented example value) |
| `metrics.replicas` | `1` | Number of Prometheus instances. One replica is enough for a demo |
| `metrics.storage.size` / `retention` | `5Gi` / `90d` | Prometheus storage size and retention, as in the example |
| `traces.sampleRatio` | `'0.1'` | Samples 10 % of traces |
| `traces.storage.backend` / `retention` | `pv` / `2160h0m0s` | PV-backed Tempo; 90-day retention |
| `alerting` | `{}` | Default Alertmanager settings |

The documentation lists the Cluster Observability Operator, Tempo Operator and Red Hat build of OpenTelemetry as
prerequisites [3]. This component therefore depends on `010-observability-operators`. Both are applied in one batch,
so the order comes from Argo CD retry and from the RHOAI operator's own reconcile loop.

**DataScienceCluster.**
The DSC uses `datasciencecluster.opendatahub.io/v2`, the API version in the 3.5 example [1]. Stage 010 manages only
`dashboard` and `workbenches` (`workbenchNamespace: rhods-notebooks` [1]). Every other component is `Removed`, so the
foundation validates before GPUs, serving or MaaS exist. `llamastackoperator` is listed as `Removed`. The live 3.5 CRD
marks it as deprecated in favour of `ogx`.

**Delegation model.**
Git keeps all components `Removed` except the two above. A later stage turns on its component by patching the live DSC
from an Argo CD `Sync` hook Job in its own Application. For that to work, `010-rhoai-platform` must not revert the
patch. Two settings on the Application ensure this:

1. `spec.ignoreDifferences` lists each delegated field as a JSON pointer, so the patched value does not show as drift [4].
2. `syncOptions: RespectIgnoreDifferences=true` makes a sync also skip those fields. Without it, Argo CD applies the
   Git value during a sync [5].

`scripts/shared/stage_apps.py delegated 010 DataScienceCluster default-dsc --group datasciencecluster.opendatahub.io`
reads the live Application and returns the delegated pointers. It returns nothing if `RespectIgnoreDifferences` is
off. Stage 020 and Stage 030 `deploy.sh` assert that their pointers are delegated before they deploy.
`validate.sh` uses the same list: it requires `dashboard`/`workbenches` Managed and the 3.5 components that are not
delegated (`sparkoperator`, `trainer`) Removed. Delegated fields and their runtime owners:

| Delegated DSC field | Runtime owner (hook Job) | Live value |
|---|---|---|
| `/spec/components/kueue` | Stage 020 `kueue/dsc-enablement/job.yaml` | `Unmanaged`, `autoCreateQueues: false` |
| `/spec/components/kserve` | Stage 030 `private-model-serving/dsc-enablement/enable-job.yaml` | `Managed` |
| `/spec/components/modelregistry` | Stage 030 `private-model-serving/model-discovery/enable-job.yaml` | `Managed` |
| `/spec/components/aigateway`, `/spec/components/ogx` | Stage 040 `maas-platform/jobs/enable-maas-job.yaml` | `Managed` |
| `/spec/components/trustyai`, `/spec/components/mlflowoperator`, `/spec/components/aipipelines` | Stage 050 `mlflow/dsc-enablement/enable-job.yaml` | `Managed` |
| `/spec/components/mcplifecycleoperator` | Stage 060 `mcp-platform/enable-job.yaml` | `Managed` |

The same model applies to `odh-dashboard-config`. Stage 030 owns `agentsCatalog`, `disableModelCatalog`,
`disableModelRegistry`, `toolCalling`, `mcpCatalog` and `mcpRegistry`. Stage 040 owns `genAiStudio`, `genAiTracing`,
`modelAsService`, `vLLMDeploymentOnMaaS`, `externalModels`, `llmdTemplates`, `guardrails`, `agentConfigManagement`,
`promptManagement`, `aiAssetCustomEndpoints` and `/spec/genAiStudioConfig`. Stage 050 owns `disableLMEval`,
`globalProjectPrompts` and `/spec/globalMLflowNamespaces`. Stage 060 owns `agentOps`. Some delegated fields have a Git
value in this folder (for example `genAiStudio: false`). That value applies only on the first creation. After that,
the owning stage's value wins.

Rules for changes:

- To delegate a field, add its pointer to the Application. Never edit the live DSC by hand.
- To remove a stage, first turn its component off through that stage. Removing a pointer from `ignoreDifferences`
  makes Argo CD restore the Git value (`Removed`) on the next sync, and that uninstalls the component.

**Auth.**
`rhods-admins` is the admin group. `rhoai-developers` (created by `010-access`) is the second user group. Together
they replace the default access for every authenticated user (`system:authenticated`) [6]. The admin and user groups
must exist in OpenShift [6]. `rhods-admins` is created by the operator, and `rhoai-developers` by `010-access`.

**OdhDashboardConfig.**
Values that differ from the documented defaults [2]:

| Field | Value | Default [2] | Reason |
|---|---|---|---|
| `connectionTest` | `true` | `false` (Technology Preview) | Lets users test S3 connections in the dashboard |
| `disableKueue` | `false` | `true` (Developer Preview) | Shows Kueue-backed hardware profiles and queues from Stage 020 |
| `disableModelCatalog`, `disableModelRegistry` | `true` | `false` | Hidden until Stage 030 delivers the registry and catalogs (delegated) |
| `modelAsService` | `false` | `true` (Technology Preview) | Hidden until Stage 040 delivers MaaS (delegated) |

`autorag`, `automl`, `agentsCatalog`, `genAiStudio` and `vLLMDeploymentOnMaaS` are set to `false`, their documented
default. `observabilityDashboard` and `disableTracking` keep their defaults (`true`, `false`). Writing them down makes
the intent visible and lets `validate.sh` check `observabilityDashboard`.

**Credentials.** None. `trustedCABundle.customCABundle` is empty.

**Cluster-specific values.** None.

## Validation

`validate.sh` checks the following:

- DSCI phase and Ready condition.
- The DSCI monitoring fields (`Managed`, namespace, replicas `1`, size `5Gi`, backend `pv`, ratio `0.1`).
- `observabilityDashboard: true`.
- The DSC is Ready at the current generation.
- The `Auth` CR is Ready at the current generation.
- Foundation component ownership, using `stage_apps.delegated`.
- The `rhods-dashboard` route answers.

`validate-foundation-services.sh` runs authenticated probes as an administrator:

- It requires exactly one Ready `Monitoring` resource.
- It queries recent `up` samples through the namespace Prometheus proxy.
- It checks that the collector service account may write the Tempo tenant (SubjectAccessReview).
- It sends one OTLP span and reads it back from Tempo by its ID.

Check by hand:

```bash
oc get dsci default-dsci -o jsonpath='{.status.phase}{"\n"}'; oc get dsc default-dsc -o jsonpath='{.status.phase}{"\n"}'
python3 scripts/shared/stage_apps.py delegated 010 DataScienceCluster default-dsc --group datasciencecluster.opendatahub.io
```
