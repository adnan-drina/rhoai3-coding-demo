# AI Coding Sandbox S3 connections (`010-sandbox-storage`)

This Application gives the AI Coding Sandbox (`demo-sandbox`) two S3 buckets on ODF and the two matching OpenShift AI
connections: **Models** (model artifacts) and **Workbench** (object exchange between workbenches). The buckets and the
connection metadata are declared in Git. A Sync hook Job copies the generated bucket credentials into the connection
Secrets at runtime, so no credential is committed. Users pick these connections in the dashboard when they create
workbenches or deploy models from the sandbox.

## Why

OpenShift AI stores connections as Kubernetes Secrets with standard annotations. An S3 connection has the keys
`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_S3_ENDPOINT`, `AWS_S3_BUCKET` and, optionally,
`AWS_DEFAULT_REGION`, plus the annotation `opendatahub.io/connection-type-protocol: s3` [1]. OpenShift AI ships a
pre-installed S3-compatible connection type [2], and workbench code reads these variables to reach the object store [3].
ODF OBCs create a bucket plus a Secret (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`) and a ConfigMap (`BUCKET_HOST`,
`BUCKET_PORT`, `BUCKET_NAME`) named after the claim [4]. The provisioner generates the credentials, so they cannot be
in Git. A small Job maps OBC output to connection keys inside the cluster.

The component is data, so it is separate from the foundation components. Its buckets and Secrets must never be pruned
or deleted with the Application.

| ObjectBucketClaim | `rhoai-workbench` | `demo-sandbox` | 0; `Prune=false,Delete=false` | Fixed `bucketName: rhoai-workbench` |
| Secret | `rhoai-models-connection` | `demo-sandbox` | 0; `Prune=false,Delete=false,ServerSideApply=true` | Connection skeleton "Models": label `opendatahub.io/dashboard: "true"`, annotation `connection-type-protocol: s3`, no data in Git |
| Secret | `rhoai-workbench-connection` | `demo-sandbox` | 0; same | Connection skeleton "Workbench" |
| ServiceAccount | `sandbox-s3-connections` | `demo-sandbox` | 0 | Identity for the hook Job |
| Role | `sandbox-s3-connections` | `demo-sandbox` | 0 | `get` on the two OBCs, their ConfigMaps and Secrets, and the two connection Secrets; `patch` on the two connection Secrets only (all by `resourceNames`) |
| RoleBinding | `sandbox-s3-connections` | `demo-sandbox` | 0 | Binds the Role to the ServiceAccount |
| Job | `sandbox-s3-connections` | `demo-sandbox` | 1; `hook: Sync`, `hook-delete-policy: BeforeHookCreation` | Waits up to 300 s per claim for `Bound` and its outputs, then patches the connection Secret's `data` |

Not in Git:

- the bucket Secrets and ConfigMaps `rhoai-models` and `rhoai-workbench`, generated by the NooBaa provisioner and owned
  by their OBCs [4];
- the credential values in the connection Secrets' `data`, written by the Job.

The hook Job stays after a successful run as evidence. Argo CD deletes it before it creates the next one [5].

## How

- **Credential mapping without exposure.** The Job uses the digest-pinned `registry.redhat.io/openshift4/ose-cli` image.
  It disables tracing (`set +x`) and uses `umask 077`. It reads the generated values and sends the patch on stdin
  (`--patch-file /dev/stdin`), so values never appear in arguments or logs.
- **Job checks before it writes.** For each claim, the Job requires the following before it writes:
  - the OBC is `Bound`;
  - the endpoint is HTTPS on port 443 and the bucket name equals the claim name;
  - the generated Secret and ConfigMap are owned by that OBC (UID match);
  - the target connection Secret carries the `010-sandbox-storage:` tracking id;
  - the patch carries the Secret's current `resourceVersion`, so a concurrent change makes it fail.

  The region falls back to `us-east-1` when the ConfigMap has no `BUCKET_REGION`.
- **Keeping runtime data out of Argo CD.** `ignoreDifferences` on `/data` keeps the Job-written credentials from
  showing as drift. `RespectIgnoreDifferences=true` keeps a sync from blanking them [6]. The two Secrets use
  resource-level server-side apply, so Argo CD owns only labels and annotations. `ClientSideApplyMigration=false`
  stops Argo CD from moving client-side field ownership, which could replay the credential fields [6]. Data objects
  carry `Prune=false,Delete=false` [6].
- **Own deploy script.** Before its first write, `deploy-sandbox-storage.sh` refuses to continue if any of the
  following is true:
  - the Stage 010 source differs from the selected, published commit (`stage_apps.py select`);
  - an existing OBC or connection Secret has an owner, is being deleted, or has another tracking id;
  - the existing Application's identity differs.

  It then applies the Application pinned to the commit, waits up to 720 s for `Synced Healthy` at that commit, and
  runs the validator.
- **Cluster-specific values.** None in Git. The bucket host comes from the OBC ConfigMap at runtime.

## Validation

`validate-sandbox-storage.sh` checks each claim and connection:

- the OBC is `Bound` and tracked by this Application;
- the generated Secret and ConfigMap are owned by the OBC;
- the bucket name matches and the port is 443;
- the connection's access keys equal the generated ones;
- the endpoint, bucket and region decode to the expected values;
- the display name, dashboard label and protocol annotation are present;
- no credentials are in `last-applied-configuration`.

It prints no values. It does not perform authenticated S3 operations.

```bash
oc get obc -n demo-sandbox rhoai-models rhoai-workbench
oc get secret -n demo-sandbox -l opendatahub.io/dashboard=true -o custom-columns=NAME:.metadata.name,DISPLAY:.metadata.annotations.openshift\\.io/display-name
```

## Alignment with official guidance

| Topic | Official guidance (link) | This repository | Status |
|---|---|---|---|
| Connection format | Secret with `opendatahub.io/connection-type-protocol: s3` and the AWS keys; `connection-type-ref` deprecated [1] | Protocol annotation only, standard keys | Aligned |
| S3 connection type | Pre-installed S3-compatible connection type [2] | Uses it; no custom connection type | Aligned |
| Bucket provisioning | OBC on `openshift-storage.noobaa.io`; ConfigMap and Secret named after the claim [4] | Same; fixed `bucketName` instead of `generateBucketName` | Aligned |
| Credentials | Generated by the OBC; Secrets hold connection data [1][4] | Copied in-cluster by a scoped Job; never in Git or logs | Aligned |
| Data retention | Resource-level `Prune=false` / `Delete=false` (upstream) [6] | Set on OBCs and connection Secrets | Aligned |
| TLS | S3 endpoints with self-signed certificates need CA configuration [3] | Endpoint is the in-cluster service `https://s3.openshift-storage.svc:443`, signed by the OpenShift service CA. This component configures no CA trust; clients rely on the CA bundles present in the project | Gap (not checked by an authenticated S3 call, see findings) |
