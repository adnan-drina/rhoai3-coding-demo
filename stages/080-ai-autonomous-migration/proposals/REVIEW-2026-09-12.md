## 1. Fragment repair: preserve the interfaces, implement the fragments

Choose explicit fragment implementations for this recovery. Do not remove the base interfaces from the specializations: ClinicServiceImpl and UserServiceImpl inject those base types. Do not approve a marker-only change: the exact generator recognizes entity-returning save methods; the base contracts declare void save(Entity). Moving those methods into intermediate Repository interfaces does not make void save a supported derived query.

Scope is the seven base contracts as one inventoried repair set. Preserve their signatures and the seven SpringData specializations. Use one concrete adapter per entity:

| Entity | Implementation scope |
| --- | --- |
| Owner | Add OwnerRepositoryImpl implementing OwnerRepository. |
| Vet | Add VetRepositoryImpl implementing VetRepository. |
| User | Add UserRepositoryImpl implementing UserRepository. |
| Pet | Extend the existing SpringDataPetRepositoryImpl to implement PetRepository as well as its existing override interface. |
| PetType | Extend the existing SpringDataPetTypeRepositoryImpl to implement PetTypeRepository as well as its existing override interface. |
| Specialty | Extend the existing SpringDataSpecialtyRepositoryImpl to implement SpecialtyRepository as well as its existing override interface. |
| Visit | Extend the existing SpringDataVisitRepositoryImpl to implement VisitRepository as well as its existing override interface. |

Keep these implementations under `src/main/java/org/springframework/samples/petclinic/repository/springdatajpa/`. Avoid adding another implementation for an already implemented delete fragment. One concrete class can implement both interfaces; the pinned generator deduplicates its injected implementation field and forwarded methods.

Two requirements are part of the scope, not later cleanup:

- Restrict each adapter's CDI bean types to its concrete implementation class, for example with `@Typed(ConcreteImpl.class)`. The generated SpringData repository must remain the sole bean satisfying each service's base-interface injection. The generator injects adapters by their concrete class. Verify this through augmentation and injection tests; the annotation recommendation alone is not proof.
- Inventory the concrete implementation of every method, including void save, owner fetch/search queries, Pet.findPetTypes, Visit.findByPetId and the four custom deletes. Fragment methods are generated before stock and annotated query methods, so an adapter can shadow the existing leaf query annotation. Preserve its actual behavior in the adapter; leaving the annotation behind does not prove it is still used. Use the frozen source for query, cascade, transaction and missing-entity semantics.

The local frozen User entity declares a String username as its @Id; the live SpringDataUserRepository declares Integer. Verify the current entity, then include the corresponding specialization ID correction in this same bounded persistence scope. Do not apply an Integer ID template blindly to all seven.

Authorized next work is preparation and isolated validation of this bounded patch, then recording it through the existing Operator-step procedure. Preserve the earlier failed attempts and Operator steps. No controller, service, schema, dependency, profile-selection or security-policy redesign belongs in this repair. If a new failure needs those paths, retain the evidence and attribute it separately.

Exit: full configured verification with tests enabled; augmentation must resolve all seven fragment contracts and service injections. Then start the packaged artifact against the decided isolated database. Exercise save/create/update and each custom delete through real transactions and read-back state, as well as representative reads. Package success alone does not prove these methods work, and HTTP parity remains a separate gate.

## 3. Automatic minting: the arbitrary-locus defect blocks it

A changing first-reported repository name must not change the repair family, write scope or retry budget on an unchanged product tree.

Minimum safe harness change: recognize this processor/cause as a set-wide failure and emit a typed blocker; never mint a one-file card from its arbitrary exception name. This is enough protection to proceed with the bounded Operator recovery above. A general family planner need not delay that manual recovery.

For autonomous handling, derive and seal the complete fragment-contract set from the type model, including leaf, parent, entity/ID and implementation relationships. Keep the original family identity and budget as members resolve. Preserve raw compiler/build messages as observations. Assess all members; disappearance of the first exception name proves nothing about the others. If repair exposes a different packaging cause, retain and route the candidate under the pending protocol; do not revert it solely because packaging still fails, and do not mark packaging PASS.

Required counterexample: repeated builds/permuted first-reported names on one product tree produce the same family or blocker identity, same scope and same budget. An incomplete type model yields unknown/blocker, not an invented complete set. Test this from the installed destination code before automatic dispatch resumes. Resume through admission/K4 only when the next failure is correctly attributed; do not complete the superseded needs_input card.
