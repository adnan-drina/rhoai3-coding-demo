# Stage 040: Governed Models-as-a-Service

## Why This Matters

A model endpoint alone does not provide a shared enterprise service. Models-as-a-Service (MaaS) gives developers governed access to private and approved external models through API keys, subscriptions, quotas and usage telemetry.

## Architecture

The private model Qwen 3.8 (`qwen3-8-27b`) is hosted in the Internal Models project on one Stage 020 RTX PRO 6000 (`g7e.2xlarge`) GPU worker with an exclusive GPU. Its replica count is a delegated live field; `stages/020-gpu-infrastructure-private-ai/deploy.sh --gpus N` starts and parks the GPU worker. Native OpenShift AI controllers connect the model to one governed Gateway with two listeners: `api` for the shared API hostname and `qwen3-8` for the model's compatibility hostname. MaaS governance stays in models-as-a-service, and external providers stay in the External Models project. The shared API hostname and `/v1` are the default for body-based model routing. The dedicated `qwen3-8` HTTPS listener remains as a compatibility endpoint; each listener keeps its explicit namespace restriction. Each admitted namespace also requires `maas-gateway-access=true`; the label alone does not grant access to another listener. Native MaaS policies control access across the same Gateway.

## What This Stage Adds

- The default private coding model `qwen3-8-27b`: Qwen 3.8 27B in Red Hat's NVFP4 build on one NVIDIA RTX PRO 6000 Blackwell (Stage 020 `gpu-rtxpro6000` profile), with MTP speculative decoding and the full 262,144-token window; it admits 16 concurrent sequences so Stage 050 evaluation requests (16 samples each) decode in one batch. The deployed quantization shows in the dashboard: the display name (`Qwen3.8 27B NVFP4`), the description (`Model id: qwen3-8-27b, quantization: NVFP4, context 262,144-token`) and the label `demo.rhoai.io/quantization`. The Model Registry lists both prepared builds, `Qwen3.8-27B-NVFP4` (linked to the deployment) and `Qwen3.8-27B-FP8`. Qwen 3.6 27B FP8 was removed on 2026-10-13.
- Native MaaS API key storage, subscriptions, authentication and token quotas.
- Reusable single-node topology and queue-routing configurations, with native NVIDIA accelerator templates.
- Approved GPT-6 Luna access through the native OpenAI external-provider integration.
- Approved NVIDIA Nemotron 3 Ultra access through the same integration against NVIDIA's OpenAI-compatible API.
- GenAI Studio enablement for experimenting with available model endpoints.
- Bounded OpenShift MCP endpoints, read-only and read-write within the caller's own permissions, for playground tool use and later coding workflows.

## What To Notice And Why It Matters

Clients use the common `/v1` base and the canonical `publishers/internal-models/models/<model-name>` local model IDs. MaaS preserves a common governance boundary. One full GPU per model is this project's model-memory choice; the configuration does not enable time slicing or automatic scaling.

The model id `qwen3-8-27b` names the model, not its quantization. The 2026-10-13 serving study measured Qwen 3.8 on the candidate GPUs and formats: on the RTX PRO 6000, the NVFP4 build reaches a 776 ms first token on 8K-token agent prompts and 302.6 output tokens per second, about 3.3 times the former L40S INT4 setup at less than half the cost per token, with coding scores equal to FP8 and within run-to-run noise of the unquantized model. Blackwell's FP4 tensor cores are what make NVFP4 the natural format here, and its small footprint leaves room for six concurrent full-window requests. An FP8 build of the same model is prepared as a one-line alternative (`040-local-models/components/qwen38-fp8`); the final choice between the two follows the next Hermes migration run.

GPT-6 Luna uses the OpenAI Chat Completions protocol. Function calls require `reasoning_effort: none`. OpenAI Responses built-in tools are outside this connection's protocol. External requests leave the cluster for the approved provider.

Native external-model access is Technology Preview. GPT-6 Luna, Claude Sonnet 5.5 and Nemotron 3 Ultra use `openai-chat`, which always uses translation rather than passthrough. Response buffering applies when translating between different API formats; it is not a blanket statement that all external responses are buffered. MaaS subscription token metering applies to OpenAI Chat Completions responses, not models configured as `messages` or `openai-responses`. Provider-key limits apply to aggregate usage by all users sharing that key, and provider entitlement is separate from gateway readiness.

External models are supported only through the default tenant. GPT-6 Luna, Claude Sonnet 5.5 and Nemotron 3 Ultra (`nemotron-3-ultra-550b-a55b`) all use `Authorization: Bearer` with each user's MaaS key on `/v1/chat/completions`. Nemotron 3 Ultra is the general-purpose model for the Gen AI playground and OpenAI-compatible IDE clients: it accepts any `max_tokens`, `temperature` and `top_p`. GPT-6 Luna (reasoning) rejects `max_tokens` and any temperature other than 1, so it needs `max_completion_tokens` from the client; the playground's MaaS providers still send `max_tokens` (RHOAIENG-90257, fixed upstream, not in 3.5.1). To use it in the playground anyway, the deploy pre-provisions a **custom endpoint** "GPT-6 Luna (Playground)" in `demo-sandbox` (`genai-studio` component: a Sync-hook Job mints a MaaS key for the `playground-sandbox` subscription owned by the `playground-maas-key-provisioner` ServiceAccount, stores it in Secret `endpoint-api-key-gpt-6-luna-maas` and writes the dashboard's `gen-ai-aa-custom-model-endpoints` ConfigMap with a `remote::openai` provider on `https://maas.<ingress-domain>/v1`), which the playground provisions without that default; add that endpoint model to the playground and set Temperature to 1 in the model settings. The deploy enables `aiAssetCustomEndpoints` and declares the ingress domain internal, so the playground's first hop (to the MaaS gateway) stays in the cluster; the gateway then sends the request to the external provider, as for any external model; the key is renewed by the next Stage 040 sync once the MaaS API no longer reports it active (keys default to the 90-day maximum), and a ConfigMap that users already extended from the UI is left untouched (add the endpoint there by hand). Claude is registered against Anthropic's OpenAI-compatible endpoint rather than the native Messages API, so no `messages` model and no gateway-wide `x-api-key` identity exist in this demo. See the [external-model formats and limitations](https://docs.redhat.com/en/documentation/red_hat_openshift_ai_self-managed/3.5/html/govern_llm_access_with_models-as-a-service/deploy-and-manage-models-as-a-service).

Stage 050 evaluates models through the same gateway: the `model-qualification` subscription and auth policy (owner `evaluated-models/evalhub-maas-key-provisioner`, the only evaluation tenant) cover both private Qwen models with a 5,000,000-token hourly quota and the three external models with 1,000,000 tokens per hour each (evaluated like the private ones and used as judge models), so EvalHub traffic is metered and attributed like any other consumer. The Stage 050 provisioner mints the key and stores it in the tenant Secret that evaluation jobs reference (`model.auth.secret_ref`).

GenAI Studio uses existing model endpoints. A user creates a playground in their project through the dashboard; the native service creates its supporting pgvector storage. Basic playground use does not add another GPU or an object-storage bucket. The fresh creation helper mounts the retained Studio PVC at its actual SQLite directory; existing playgrounds require private backup and native restore before changing persistence. RAG, AutoRAG and AutoML are outside this stage.

## How Red Hat And Open Source Make It Work

OpenShift AI manages AIGateway, KServe and OGX. Red Hat Connectivity Link supplies native authentication and rate limiting. Service Mesh and Gateway API provide routing. PostgreSQL stores MaaS API-key state. GitOps owns customer configuration while native operators own generated workloads.

## Trust Boundaries

Provider keys and database credentials stay outside Git. Each model request must use its authorized MaaS key. OpenShift MCP exposes only the selected read-only tools and retains Kubernetes RBAC restrictions. Browser checks use your own session.

## Red Hat Products Used

Red Hat OpenShift AI 3.5, OpenShift Container Platform 4.22, Red Hat Connectivity Link 1.4 and OpenShift Service Mesh 3.4. Native external-model integration and GenAI Studio retain their documented product support status; upstream MCP is a separately pinned project component.

## Deploy And Validate

`deploy.sh [--revision REF]` deploys the reviewed published commit (default `GIT_REPO_BRANCH`, then `HEAD`) through the shared flow in `scripts/stage-apps.sh`. It starts a hook-strategy sync of each component whose current source has not been synced yet, creates the provider and database credentials in the cluster, and waits until every component is Synced and Healthy at that commit. No Argo CD CLI is needed.

The default deployment selects eight Argo CD Applications, one per component, all at the same reviewed revision: `040-maas-operators`, `040-maas-database`, `040-gateway-governance`, `040-maas-platform`, `040-local-models`, `040-external-models`, `040-model-access` and `040-genai-studio`. Switching a model or changing who may use it syncs only that component. A ninth Application, `040-showback-demo`, is optional and manually synced through explicit component selection. Its corrected release `adecf57cab87982f5b5a48c966860376474f8f62` serves the reviewed Qwen R2 report through one Ready publisher with verified native financial scraping. Native inputs remain inert and the Mistral draft is excluded.

```bash
./stages/040-governed-models-as-a-service/deploy.sh
./stages/040-governed-models-as-a-service/validate.sh --readiness
```

`deploy.sh` ends by registering the deployed model and its prepared format alternates in the model registry (idempotent, never overwriting a record).

Readiness checks do not establish inference, streaming or quota behavior. Bounded functional checks and user playground interaction complete acceptance. In the dashboard, create a playground in your project and select an available governed model endpoint. Do not use the playground to create a replacement serving deployment.

To qualify just one approved external model with one completion, set `RHOAI_STAGE040_MODEL=nemotron-3-ultra-550b-a55b` (or `gpt-6-luna`, `claude-sonnet-5-5`) and `RHOAI_STAGE040_SINGLE_COMPLETION=true` when running `stages/040-governed-models-as-a-service/validate.sh --functional`, together with `RHOAI_STAGE040_PERSONA_KUBECONFIG` and the reviewed deployed revision. This scope does not run local models, streaming or tool-call tests. Its temporary key is revoked afterward.

## Direct Catalog MCP Connection

In **Gen AI studio → Playground → MCP**, select **OpenShift-MCP** (read-only, no token needed) or **OpenShift-MCP-ReadWrite** while using project **AI Coding Sandbox**. The read-only server (`openshift-mcp-server`, 13 core/config tools, Secrets and writes denied) is an in-cluster endpoint: without a token it acts as its bounded ServiceAccount (`view` on the demo projects plus namespace, project, node and metrics listings), and with your own OpenShift token (`oc whoami -t` via **Authorize**) it acts as you. The read-write server (`openshift-mcp-server-rw`, same image) is on a public HTTPS Route and always requires your token: it adds create, update, scale, delete, exec and run tools, every action authorized by the Kubernetes API as you, Secrets still denied. Tokens are session-only; never enter a model MaaS API key. Both appear under **AI asset endpoints → MCP servers**: external clients use the read-write endpoint with their own token, in-cluster clients such as Dev Spaces workspaces can also use the read-only endpoint without one. Pick a model that calls tools: Qwen 3.8, Claude Sonnet 5.5 and Nemotron 3 Ultra return tool calls through the gateway; GPT-6 Luna rejects function tools on chat completions unless `reasoning_effort: none` is sent, which the playground cannot do. Qualified on 2026-10-09 outside the browser: the read-write server answers 401 without a bearer and, with a user token, lists 19 tools, created, read and deleted a scratch ConfigMap in `demo-sandbox` through its tools, and refused a Secret read; the read-only server lists 13 tools without a token and acts as its bounded ServiceAccount. Both discovery keys are published and validated by readiness. The separate **MCP servers** hosting project and Registry are accessible to `ai-admin`; `ai-developer` consumes tools using its own project permissions without hosting access. The legacy Stage 040 server (`rhoai-mcp`, entry `OpenShift-MCP`) was retired on 2026-10-09.

This follows the [documented MCP connection procedure](https://docs.redhat.com/en/documentation/red_hat_openshift_ai_self-managed/3.5/html-single/experimenting_with_models_in_the_gen_ai_playground/index). It is a direct HTTPS connection, not MCP Gateway aggregation or MaaS API-key/quota governance. Gateway qualification is tracked separately.

Both discovery fields are published by `stages/040-governed-models-as-a-service/deploy.sh`; exact Argo field delegation preserves them, every deploy republishes them (a no-op when unchanged), `validate.sh` detects drift, and a reviewed change of a published field needs [`studio-mcp/publish.sh --replace`](studio-mcp/README.md). This is customer-managed field publication, not operator synchronization from the Registry. Retain its private UID-scoped ownership journal for repeated deployment. Stage040 does not require Stage060 on a fresh foundation: publication defers while the catalog runtime is absent, and Stage060 explicitly publishes once ready.

### Claude Sonnet 5.5

Claude Sonnet 5.5 uses the documented Anthropic provider with `apiFormat: openai-chat` and `path: /v1/chat/completions`, Anthropic's [OpenAI-compatible endpoint](https://platform.claude.com/docs/en/api/openai-sdk). The gateway forwards OpenAI Chat Completions unchanged and receives OpenAI-format responses with `usage.total_tokens`, so Claude is subscription-token-metered and streams like the other external models. Supply `ANTHROPIC_API_KEY` privately; deployment creates `anthropic-provider-api-key` through standard input. The exact provider model ID must be available to that key; catalog readiness alone does not prove provider entitlement or inference. The three personal subscriptions include Claude; DevSpaces remains local-only.

Use the discovered model endpoint with `/v1/chat/completions`, `"model": "claude-sonnet-5-5"` and your MaaS key in `Authorization: Bearer`. Anthropic documents this endpoint for testing and comparison: `response_format`, `logprobs`, `n > 1`, penalties and `seed` are ignored, prompt caching is unavailable and system messages are hoisted into one system prompt; use the native Messages API outside the gateway when those matter. Claude 5.x accepts only the default temperature (`1`) and rejects `top_p`: in the Gen AI playground set **Temperature to 1** (the default is 0.1); API clients must send `temperature: 1` or omit it, and never `top_p`. This selection also keeps Claude clear of a Connectivity Link 1.4.3 gateway limitation described in the [troubleshooting guide](../../docs/TROUBLESHOOTING.md#maas-gateway-holds-a-response-open-until-the-client-times-out). ### Nemotron 3 Ultra 550B

NVIDIA's hosted inference API is OpenAI-compatible, so [`nvidia/nemotron-3-ultra-550b-a55b`](https://build.nvidia.com/nvidia/nemotron-3-ultra-550b-a55b) is registered the way the [MaaS guide](https://rh-aiservices-bu.github.io/rhoai-maas-guide/modules/main/08-external-models.html) registers third-party providers: an `openai` ExternalProvider with endpoint `integrate.api.nvidia.com` and an ExternalModel with `apiFormat: openai-chat`, `path: /v1/chat/completions` and `targetModel: nvidia/nemotron-3-ultra-550b-a55b`. Clients request `nemotron-3-ultra-550b-a55b`. Supply `NVIDIA_API_KEY` privately (an NVIDIA API key from build.nvidia.com); deployment creates `nvidia-provider-api-key` through standard input. NVIDIA returns OpenAI-format usage, including the trailing usage chunk when the gateway asks for it, so the model is subscription-token-metered and streams like the other external models. The three personal subscriptions include it at the same hourly token budget as the other external models.

The model reasons by default: responses carry `reasoning_content` beside `content`, and reasoning tokens count toward the completion tokens the gateway meters. It accepts `max_tokens`, `temperature` and `top_p`, so the Gen AI playground can use it through its normal MaaS provider path without a custom endpoint. NVIDIA's shared endpoint answers `503 Service temporarily overloaded` under load; the OpenAI SDKs and the playground retry those, direct scripts should retry once.
